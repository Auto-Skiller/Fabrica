# Mission & Task Management Architecture (`missions_arch.md`)

This document provides a complete, production-grade architectural audit and logic walkthrough for the Missions, Workspace Artifact Sync, and Pipeline Processing Subsystem.

---

## 1. Subsystem Overview & Mission Pipeline Architecture

The Missions Subsystem orchestrates goal-oriented agent tasks ("Missions"). Missions pass through standard pipeline stages (`discovery` ➔ `blueprint` ➔ `scaffold` ➔ `execute` ➔ `review`). Artifacts generated by the agent reside inside `workspace/Sources/` and `workspace/Deliverables/` across any custom directory paths the agent creates.

The `missions/<mission_id>/` directory is strictly reserved for **runtime agent temp scripts** that users do not see. `planning/` and `execution/` subdirectories have been completely removed from `missions/<mission_id>/`.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           Frontend Client UI                                │
│   - Mission Management Drawer / Task Roadmaps                               │
│   - Pipeline Stage Movement & Action Triggers                               │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ HTTP Requests (frontend-next/components/missions/api.ts)
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                       Missions Express API Routes                           │
│                     (src/api/routes/missions.routes.ts)                     │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                           Core Missions Engine                              │
│                          (src/core/missions.ts)                             │
│  - Temp Script Directory Scaffolder (ensureMissionWorkspaceDirs)            │
│  - Reads Sources & Deliverables directly from workspace.json index          │
│  - Real-time Store Synchronizer (syncMissionsJson)                          │
│  - Pending & Action Event Stream Manager                                    │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ Workspace Filesystem & Index Writes
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│                   Tenant Storage (workspaces/<tenant_id>/)                  │
│  ├── missions.json  (Single index: { missions, pendings, actions })         │
│  ├── missions/<mission_id>/  (Runtime agent temp scripts — hidden)          │
│  └── workspace/                                                             │
│      ├── Sources/       (Scanned dynamically for all source files)          │
│      └── Deliverables/  (Scanned dynamically for all deliverable files)     │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 2. Component Architecture (`components_arch`)

Located in `frontend-next/components/missions/`:

### A. Data Types & Interfaces (`frontend-next/components/missions/types.ts`)

- **`MissionClass`**: Stage classification `'DRAFT' | 'PLANNING' | 'EXECUTION' | 'DONE'`.
- **`Priority`**: Priority level `'CRITICAL' | 'HIGH' | 'MEDIUM' | 'LOW'`.
- **`MissionGoal`**: Detailed goal metadata:
  - `status: boolean`: Completion status.
  - `priority: Priority`: Urgency.
  - `goal: string`: Main statement.
  - `why / cause / how: string`: Rationale and methodology.
  - `benefits / costs: string[]`: Trade-off analysis.
  - `worth_it: string`: Cost-benefit evaluation result.
  - `instructions: string[]`: Actionable step-by-step guidance.
- **`MissionTask`**:
  - `priority_ref: number`: Numerical order.
  - `progress: 'completed' | 'in-progress' | 'blocked' | 'not-started'`: Task progress.
  - `task: string`: Task title.
  - `instructions: string[]`: Sub-instructions.
  - `depends_on?: string[]`: Dependency array linking to prerequisite task IDs.
- **`Mission`**: Frontend model holding objective, priority, state, metrics, goals, and tasks map.
- **Legacy Components Note**: Both `DependencyGraph` and `MissionsYaml` have been entirely removed from the codebase and architecture.

### B. Frontend API Wrapper (`frontend-next/components/missions/api.ts`)

- **`missionsApi` Methods**:
  - `getMissions()`: `GET /api/missions` — Fetches array of all active missions.
  - `createMission(title, objective, type)`: `POST /api/missions/create` — Provisions new mission.
  - `updateMission(id, updates)`: `POST /api/missions/update` — Updates mission metadata or tasks.
  - `deleteMission(id)`: `POST /api/missions/delete` — Deletes mission and cleans up workspace.
  - `getMissionSchema(type)`: `GET /api/missions/schema` — Loads stage definition schema.
  - `saveDbMission(mission)`: Smart helper routing to `createMission` or `updateMission`.

## 3. Routes Architecture (`routes_arch`)

Located in `src/api/routes/missions.routes.ts`:

| Method | Endpoint | Description | Request Body | Response Schema |
| :--- | :--- | :--- | :--- | :--- |
| `GET` | `/api/missions` | Lists all active tenant missions | Query: `?tenantId=...` | `{ ok: true, missions: Mission[] }` |
| `GET` | `/api/missions/data` | Returns unified store data (missions + pendings + actions) | Query: `?tenantId=...` | `{ ok: true, missions, pendings, actions }` |
| `POST` | `/api/missions/clear-pending` | Clears pending flag for a mission | `{ id: string }` | `{ ok: true }` |
| `POST` | `/api/missions/create` | Provisions a new mission & flags Pending | `{ title, objective, type? }` | `{ ok: true, mission: Mission }` |
| `POST` | `/api/missions/update` | Updates mission metadata/stage & records Action | `{ id: string, ...updates }` | `{ ok: true, mission: Mission }` |
| `POST` | `/api/missions/delete` | Purges mission and folder & records Action | `{ id: string }` | `{ ok: true }` |
| `GET` | `/api/missions/schema` | Fetches pipeline stage schema | Query: `?type=standard` | `{ ok: true, schema: MissionSchema }` |

## 4. Core Architecture (`core_arch`)

Located in `src/core/missions.ts`:

### A. TypeScript Interfaces

- **`MissionArtifactItem`**: `{ name: string, path: string, processed: boolean, size?: number, modified_at?: string }`
- **`Mission`**: Frontend & backend model holding objective, priority, stage, phase, scratchpad, sources (`MissionArtifactItem[]`), deliverables (`MissionArtifactItem[]`), goals, and tasks map.
- **`MissionTask`**: `{ id, title, cost?, benefit?, worth_it?, completed, assigned_agent?, deliverable_path? }`
- **`MissionBlueprint`**: `{ id, title, objective, type, status, phase, qa_state?, tasks }`
- **`MissionSchema`**: Stage definition object with storage paths and pipeline stages (`["discovery", "blueprint", "scaffold", "execute", "review"]`).
- **`MissionsStoreData`**: `{ missions: Mission[], pendings: MissionPendingItem[], actions: MissionActionItem[] }`.

### B. Artifact Creation & Synchronization Engine

- **`getMissionSchema(missionType)`**: Returns normalized mission schema configuration.
- **`ensureMissionWorkspaceDirs(tenantId, missionType, missionId)`**:
  - Scaffolds `workspaces/<tenant_id>/missions/<mission_id>/` strictly for agent runtime temp scripts.
  - Ensures phase output directories (`workspace/Sources` and `workspace/Deliverables`) exist.
- **`scanWorkspaceArtifacts(tenantId, existingMission?)`**:
  - Delegates to `workspace.ts` (`getWorkspaceArtifactsFromIndex`) to fetch `sources` and `deliverables` directly from `workspace.json`.
  - Maps items into `MissionArtifactItem` format (`name`, `path`, `processed`, `size`, `modified_at`).
  - Preserves user/agent `processed` toggle status for each item across syncs.
- **`syncMissionWorkspaceArtifacts(mission)`**:
  - Dynamically updates `sources` and `deliverables` lists for the mission based on live filesystem scanning.
  - Triggers `saveMissionToStore(tenantId, updatedMission)` to synchronize `missions.json`.
- **`syncMissionsJson(tenantId)`**:
  - Real-time syncs `workspaces/<tenant_id>/missions.json`.
  - Guarantees each active mission has a runtime scratchpad folder in `missions/<mission_id>/` and dynamically scanned `sources` and `deliverables` arrays.
- **`createMission(tenantId, { title, objective, type })`**:
  - Generates unique ID `msn_<timestamp>_<random>`.
  - Initializes phase to `'discovery'` and status to `'drafting'`.
  - Scaffolds runtime temp directory `missions/<mission_id>/`.
  - Instantly flags mission as `Pending` in `pendings` array of `missions.json`.
  - Instantly records `created` action in `actions` array of `missions.json`.
- **`updateMission(tenantId, missionId, updates)`**:
  - Applies partial updates and resynchronizes workspace artifacts.
  - Automatically detects pipeline stage/phase changes, executes file moving operations via `moveUserFile` (`/api/workspace/file/move`), updates item stage and path in `workspace.json`, and records `action: 'moved'` (or `action: 'updated'`) in `actions` array of `missions.json`.
- **`deleteMission(tenantId, missionId)`**:
  - Removes runtime temp directory `workspaces/<tenant_id>/missions/<missionId>/`.
  - Deletes associated mission deliverable files via `deleteUserFile` (`/api/workspace/file/delete`) and removes item state from `workspace.json`.
  - Instantly records `action: 'deleted'` in `actions` array of `missions.json` and resynchronizes `workspace.json`.

### B. Mission Folder Hierarchy:

```
workspaces/<tenant_id>/
├── missions.json                              # Central real-time mission index (missions, pendings, actions, sources, deliverables)
├── missions/
│   └── msn_1772467200000_3x8a/               # Runtime agent temp scripts ONLY (hidden from users)
└── workspace/
    ├── Sources/                               # Scanned recursively for all source items
    │   └── <custom_subfolders>/               # Custom paths generated dynamically by the agent
    └── Deliverables/                          # Scanned recursively for all deliverable items
        └── <custom_subfolders>/               # Custom paths generated dynamically by the agent
```
